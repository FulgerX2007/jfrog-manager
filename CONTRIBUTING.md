# Contributing to JFrog Manager

Thanks for contributing. This guide covers how to propose changes and the gates a
change must pass — including the documentation it must carry.

> Audience: contributors (human and AI).

## Getting set up

Prerequisites: Go 1.26+ (`README.md`; `go.mod` pins `go 1.26.1`) and a JFrog
Artifactory instance with an access token (`README.md`).

```bash
cp .env.example .env && chmod 600 .env   # then fill in JFROG_URL, JFROG_USERNAME, JFROG_TOKEN
go mod tidy                              # install dependencies
go test ./...                            # run all tests
go run main.go                           # start the server (default port 8080)
```

Extra local setup, as documented in `README.md`, `CLAUDE.md` and `.env.example`:

- **Environment variables.** Configuration is env-only, loaded from `.env` in the
  working directory (`internal/config/config.go`). `JFROG_URL`, `JFROG_USERNAME` and
  `JFROG_TOKEN` are required; `PORT` (default `8080`), `TIMEOUT` (default `30`
  seconds), `DEFAULT_REPO` and `GIN_MODE` (default `release`) are optional
  (`README.md`). `.env` is gitignored (`.gitignore`) — never commit it.
- **Run from the repository root.** Templates are not embedded; `main.go` loads them
  from the relative directory `templates`, so `go run main.go` must be started from
  the repo root (`CLAUDE.md`).
- **Services and fixtures.** The test suite needs no external services: tests use only
  the standard library, and `internal/jfrog` tests run the real client against an
  `httptest.Server` (`CLAUDE.md`). No database is used.
- **Linter.** The lint command is `golangci-lint run`; the repository ships no
  `.golangci.yml`, so the default linters apply (`CLAUDE.md`).

## Commit messages

Use **Conventional Commits** (`type: subject` or `type(scope): subject`). The types
seen in `git log` and `.goreleaser.yaml` are `feat`, `fix`, `docs`, `test`, `chore`
and `ci`.

The prefix is functional, not cosmetic: release notes are generated by GoReleaser
from commit subjects (`.goreleaser.yaml`, `changelog` section):

| Commit prefix | Release-notes group |
|---|---|
| `feat:` / `feat(scope):` | Features |
| `fix:` / `fix(scope):` | Fixes |
| `docs:`, `test:`, `chore:`, `ci:` | excluded from the release notes |
| anything else | Others |

The exclusion patterns in `.goreleaser.yaml` match the bare prefix followed by a
colon (`^docs:`, `^test:`, `^chore:`, `^ci:`), so a scoped form such as `docs(readme):`
is not excluded and lands under *Others*.

No CI job or commit hook validates commit messages — the only workflow in the repo is
the tag-triggered release (`.github/workflows/release.yml`). Nothing in
the repo enforces the convention.

## Quality gates (run before opening a PR)

```bash
golangci-lint run               # lint / format
go test ./...                   # tests
go build -o jfrog_manager .     # build
```

These commands are taken from `CLAUDE.md` (`go test ./...` is also in `README.md`, *Testing*). The repository
has no Makefile and no test or lint CI workflow, so **these gates are not enforced
automatically** — run them locally before every PR. The only workflow,
`.github/workflows/release.yml`, runs on pushed `v*` tags and executes
`goreleaser release --clean`; it does not run on pull requests.

Useful variants (`CLAUDE.md`):

```bash
go test ./internal/handlers -run TestUploadArtifact_Success -v   # single test
go test -coverprofile=coverage.out ./... && go tool cover -html=coverage.out
```

`coverage.out` and the `jfrog_manager` binary are gitignored (`.gitignore`).

Things that break the build or tests if missed (`CLAUDE.md`):

- Adding a method to `jfrog.Service` (`internal/jfrog/service.go`) requires updating
  both mock implementations: `mockService` in `main_test.go` and in
  `internal/handlers/artifacts_test.go`.
- Routes are registered in three places: `setupRouter` in `main.go` and the test
  routers in `internal/handlers/artifacts_test.go` and `internal/handlers/xray_test.go`.

## Documentation duties

**Every change must keep docs in sync.** Before requesting review, run the matching
checklist and confirm:

- [ ] **New feature** → updated `README.md` (if user-facing), `ARCHITECTURE.md`
      (if structure changed), `docs/api/` (if API changed), and `CHANGELOG.md`.
- [ ] **Bug fix** → `CHANGELOG.md` entry under *Fixed*; doc corrected if it was wrong.
- [ ] **Significant decision** → an ADR in `docs/decisions/`.

See `.ai/rules.md` for the full list.

`CHANGELOG.md` is maintained by hand and is separate from the GitHub release notes
that GoReleaser generates from commit subjects (see *Commit messages*).

Project-specific reminders:

- A new or changed HTTP route must be reflected in the *Routes* table in `README.md`.
- A new or changed environment variable must be reflected in `.env.example` and the
  variable table in `README.md`.
- Agent-facing guidance (commands, architecture notes, conventions) lives in
  `CLAUDE.md`; update it when those change.

## Pull request checklist

- [ ] Conventional commit messages
- [ ] Lint + tests pass locally
- [ ] Docs updated per the duties above
- [ ] `CHANGELOG.md` has an `[Unreleased]` entry
- [ ] No secrets, credentials, or generated artifacts committed
      (`.env`, `coverage.out`, the `jfrog_manager` binary, `payload.json` and `dist/`
      are gitignored — see `.gitignore`)

## Releases

Releases are cut by pushing a git tag matching `v*`, which triggers GoReleaser
(`.github/workflows/release.yml`, `.goreleaser.yaml`). Contributors do not need to
build release artifacts by hand.
